## G. WiFi / 距離（新增 · 待你討論）

> ⚠️ **已被 §J 更新**：去陸製 → 無 ESP32 → STM32 無內建 WiFi，**頂層/跨段預設改 Ethernet（W5500）**，不走 WiFi。以下 WiFi 討論僅在日後找到非陸製 WiFi 模組時才適用。

> 你的疑問：末端距離較遠是否要用 WiFi？中間層需不需要 WiFi？

**先破一個迷思：RS485 本身就很適合長距離**。它是差動匯流排，低 baud 下可拉到約 **1200 公尺**。所以「單純距離遠」通常**直接拉 RS485 線就好，不需要 WiFi**。

WiFi 在這套系統只有**兩個真正的用途**，而且是「**替換某一段連結**」，不是每層都要：

1. **頂層對 PC 的頻寬紓解**（你的點 11）：樹很大時，PC 端 RS485 接收會排隊 → 讓「頂層中繼器 ↔ PC」這一段改走 WiFi/Ethernet（ESP32 內建 WiFi 最省事）。樹內部仍走 RS485。
2. **拉不了線的物理斷點**：某個分支在**另一棟廠房 / 會旋轉或移動的設備**上，纜線過不去 → 在那個分支點放一台「**WiFi 橋接中繼器**」，把**那一段連結**從 RS485 換成 WiFi。

**關鍵好處**：因為 `\n`/`\r` 框架和位址系統**與傳輸媒介無關**，WiFi 只是把某段連結的 bytes 改用 TCP/UDP 送，**協定、定址、cache 邏輯完全不變**——這正是[模組 F 傳輸層抽象](04_軟體模組拆分.md)要做的事。一台 ESP32 同時有 WiFi + RS485，所以「橋接中繼器」＝一台 ESP32：下層 RS485、上層 WiFi。

**中間層需不需要 WiFi？** 預設**不需要**。中間層走 RS485 又快又穩又便宜。只在「①頂層對 PC」或「②某個拉不了線的分支」才點名用 WiFi。

**取捨提醒**：WiFi 有延遲/抖動、要處理斷線重連，不像 RS485 那麼即時可預期；工廠可靠度優先，能拉線就拉線，WiFi 當「跨不過去時的橋」。好在 cache 樹在這裡幫大忙——WiFi 橋接的子樹即使斷線也還在本地輪詢+快取，重連後直接把 cache 給上去。

**待你決定**：目前是否已有「跨棟 / 移動設備 / 頻寬爆掉」任一情境？沒有的話，**先全走 RS485**，把模組 F 的 `Link` 介面留好接口即可，等真的遇到再插 WiFi 實作。

## H. 拓樸韌性 / 前端冗餘（定案 2026-08-19）

### H0. 容量與兩道「牆」
- **定址**：每 bus 64 位址、保留 1（廣播/其他功能）→ **63 可用**；分層字串位址長度不限 → 定址幾乎無上限，最大末端 = **63^D**（D=bus 層數）。
- 真正的上限**不是定址**，是：
  - **牆 A｜頂層頻寬（限制總設備數）**：PC 拉整包 cache 時，頂層鏈路要吐「全部末端」。純有線 MAX13487(500kbps) ≈ 1,250 筆/秒 → 秒級整包刷新的實務天花板**約 2 層（數千台）**。要更大 → PC 改「要指定位址」不拉整包，或頂層換 Ethernet/WiFi（模組 F）。
  - **牆 B｜端到端新鮮度延遲（限制層數）**：cache 讓各層解耦，葉端新鮮度 ≈ 自己那條 bus 一圈；新值「冒到 PC」≈ 層數 × 一圈。高 baud 下層數牆很寬，通常先撞牆 A。
- 計算/驗證腳本：`sim/capacity.py`（63^D 表）、`sim/link_budget.py`（頻率/延遲/牆）、`sim/simulate.py`（走真實 `lib/protocol.py` 的資料流模擬）。

### H1. 分層韌性策略（依故障半徑分配冗餘）
- **看門狗（全體，零硬體成本）**：每台 ESP32 開硬體 watchdog，韌體卡死/暫態自動重開——CP 值最高的一招。
- **溫備援（多數節點）**：預載 JSON、撥同址、壞了插上頂替；搭配 **PC 端新鮮度告警**（cache 帶時戳、過期標紅）讓人及時換。用於故障半徑小的葉端。
- **熱備（只押頂層 1~2 層）**：故障半徑最大的節點才上自動 failover。

### H2. 前端中繼器（PC 下那台）＝熱備
本系統**唯一的全樹單點**，冗餘預算優先押這裡。

- **熱備機制**：主+備兩台；備機平時**被動偷聽第 1 層 bus** 保溫 cache；PC 連續 N 次逾時 → **PC 當仲裁**點名備機接手、備機升為第 1 層 master。仲裁權在 PC → 不會雙主。
- **上行（PC ↔ 前端）＝兩條點對點快速 RS485（選項 A，定案）**：
  - ESP32 端用帶方向控制的快速收發器（THVD1450 / MAX3485 級，多 Mbps），PC 端用 USB-RS485 轉接頭；**每台一條獨立 P2P 線**。
  - 好處：速度比 MAX13487 快 ~10×（把牆 A 外推一級）＋兩條獨立線＝**PC 側鏈路也冗餘**＋PC 對兩台獨立問，split-brain 最單純。
  - **刻意偏離全系統「免 DE/RE」慣例**：此鏈路為求速度採方向控制；因點對點只有兩端、轉向時序最單純，可接受。其餘 multidrop bus 仍用 MAX13487。
- **下行（後端）＝主+備共掛同一條第 1 層 bus**：
  - 後端**零複製**：兩台的下行收發器（MAX13487）接同一對 A/B 線，都只是這條 bus 上的 drop。
  - **master 不佔位址** → 第 1 層 bus 仍 **63 台**孩子。（註：若改用「主機把備機當心跳孩子輪詢」的做法才會 −1 = 62；本設計用「偷聽 + PC 仲裁」，維持 63。）
  - **防撞線**：同時只有一台在發；備機被提升前，對第 1 層 bus 的 UART **保持靜默**（MAX13487 AutoDirection：不發即不驅動匯流排）。
- **已知缺口**：第 1 層 bus 的**共享纜線本身仍是單點**（斷線則斷點後全失聯）。要連纜線也保護需環網 / 雙 bus，**暫不做**，先標記。

## I. 邊緣控制 / PID 放置（新增 2026-08-20）

**架構演進**：末端模組不只是傳感器，而是「**感測 + 作動 + 本地控制**」三合一（帶 MCU）。工廠端作動以**驅動馬達**與**控溫訊號**為主，需要 **PID 閉環**。

### 已定
- **PID 放本地（邊緣）**：閉環跑在**末端模組自己**的 MCU 裡（讀自己的感測器 → 算 PID → 驅動自己的馬達/加熱）。**確定不放 PC**（PC 太忙，且網路延遲不該進控制迴路）。
- **放置策略＝「I/O 在哪就在哪控」，中間層只為「協調」而非「慢」**：
  - 快迴路（馬達 ms 級）→ **硬約束，一律末端**。
  - 其他**單一迴路**（感測+作動同在一台末端）→ **預設也放末端**，不分快慢（最穩、fail-operational、無網路在迴路）。
  - **只有需要「跨多個末端一起算」的控制**（串級 / 多區統籌）才上移中繼器/RPi；這類天生是慢迴路、容忍跨網延遲。負責很多區 → MCU 升**樹莓派**。
  - → 修正原「快末端/慢中繼器」講法：**慢的「單一」迴路仍該在末端**；把迴路上移的理由是「要協調多個末端」，不是「它慢」。
- **PID 參數/設定點來源＝兩者**：PC 下發設定點/增益（遠端可調）＋ 末端本地存一份預設（`CFG`/指撥，斷線也照跑）。
- **中繼器收發器：上、下行各一顆 RS485 IC + 各一支 UART**，**不可用一顆同時串上下**。理由：上下層是**兩條電氣獨立的 bus**——這樣分層才有意義（各段獨立 63 位址、頻寬互不干擾、cache 樹解耦）；一顆串接會把上下併成同一條大 bus、層級失效。ESP32 三個 UART 夠用；RPi 硬體 UART 少，2 條 bus 以上需加 USB-serial / UART HAT。
- **韌體依末端群組位址順序做 I/O**：跑多迴路的節點以**位址順序**掃描（PLC 式 scan cycle），順序與時序要確定；單一末端本地控制則是它自己的事。

### 關鍵工程含義（本次 review 補充）
1. **網路角色 = 監督(supervisory)，不是控制路徑**。控制閉環在本地、以本地速率跑（例如 10–100 Hz）；RS485 只做兩件事：**上行回報狀態**（PV / 設定點 / 輸出%）、**下行改設定**（設定點、PID 增益、模式、啟停）。→ **控制不吃輪詢節奏**，之前「輪詢新鮮度會不會拖累控制」的疑慮在此解消。這就是工業界「本地迴路 + SCADA 監督」的標準分工。
2. **放置依迴路速度**：
   - **快迴路（馬達位置/速度，毫秒級）→ 必須在末端**，網路絕不能在迴路裡。
   - **慢迴路（溫度/壓力/液位，秒~分級）→ 末端或中繼器/RPi 皆可**，網路延遲可容忍。
   - ⚠️ 中繼器/RPi 跑多區 PID **只有當該迴路的感測+作動是它的本地 I/O 才行**；若感測器與作動器在下游末端、跨 RS485，輪詢延遲會被吃進閉環 → 只適合慢迴路。
3. **Fail-operational（本地 PID 的大優點）**：上層/網路斷線時，末端**照最後設定點繼續控制**、不停擺。配合**廣播位址 0 = 緊急停止** → 一聲令下全體輸出進 `safe_state`。斷線行為（維持 vs 進 safe_state）用 schema 的 `output.safe_state` 定義。

## J. 元件選型 / 去陸製 → STM32（新增 2026-08-20）

**合規約束**：台灣端要**去陸製（no China-origin）元件** → **ESP32（Espressif，中國上海）不能用** → 主控 MCU 改 **STM32（STMicroelectronics，歐洲）**。

### 已定
- **主控 MCU：ESP32 → STM32**（末端與中繼器皆是）。手上已有 STM32 + Nucleo，可直接開發。
- **樹莓派只放最末端**（當「複雜多迴路的邊緣控制器」），**不放中間層**；中間層中繼器 = 單純 STM32（路由 + cache）。（RPi 產於英國、SoC Broadcom 美國，非陸製 OK。）
- **非陸製 BOM**：MCU=STM32(歐)／很簡單的末端也可用 AVR·ATmega(Microchip 美)；RS485 收發器 MAX13487 或 THVD1450(ADI/TI 美)；RPi(英/美)。→ 原本唯一陸製件就是 ESP32，換掉即整套非陸製。

### 關鍵影響
1. **WiFi 沒了 → 改 Ethernet**。STM32 無內建 WiFi（WB=BLE、WL=LoRa，都不是）。§G 的「WiFi 橋接」改路線：**首選 STM32 + WIZnet W5500**（韓，SPI 介面、內建硬體 TCP/IP，任何 STM32 可掛）→ 非陸製，又剛好工廠骨幹本就走 Ethernet。媒介與 `\n`/`\r` 協定無關（模組 F），換 Ethernet 協定/定址/cache 不動。

## K. 快取行為 + 末端 JSON 複雜度（澄清 2026-08-20）

### 快取：hold-last-value（保持最後良值）
- 輪巡時上層**一律直接撈快取的值**；某台這輪來不及更新（逾時）→ **保留上一筆舊值**繼續給，不清空。
- ⚠️ **但每筆要帶新鮮度標記**（時戳 / age / fresh-stale 旗標），讓 PC/控制端能分辨「這是 3 秒前的舊值」還是「剛更新」。否則感測器死掉會看起來永遠正常——對控制/安全很危險。
- **待修正**：目前 sim/firmware 是「逾時就跳過(None)」，要改成「保留舊值 + 標 age」；docs/02 §4 一併更新。

### JSON 複雜度不對稱
- **中繼器 JSON 很簡單**：它是路由節點（`role:"relay-node"` + id），本身沒有量測。（它另外**存一份「所有已知末端 JSON」的庫**來辨識下層——那是兩回事。）
- **末端 JSON 複雜**：一台末端可對應**很多感測器 / ADC 通道** → `measurements` 陣列很多筆。建議 schema（模組 E）補：
  - 每筆量測加 `channel`/`adc`（對到哪個 ADC 腳/通道），讓末端韌體能資料驅動。
  - **校正改成「每筆量測各自一組」**：現在 `calibration` 在設備層＝全機一組 slope/offset；多感測器需**每個 ADC 各自校正**。

### 設備型別型錄（catalog）＝一個大檔，支援直接替換（已定）
- **一個很大的 JSON 檔**收全部設備描述：中繼器條目**簡單**、末端條目**複雜**，但**同一個檔**（不是一堆小檔）。因為設備用 **JSON 描述、非寫死程式**，**新設備＝往這檔加一筆**、韌體/PC 不用改。
- **原始用意（需求 16）**：型錄預載進中繼器 + 指撥定址 → **插上任意位置的末端/感測器/中繼器，系統靠「型錄 + 該位址」就知道這位置本來該是什麼、幹什麼用 → 直接替換**、免重寫。
- **末端不自存完整 JSON**：末端只認自己的位址（指撥）；完整說明書在型錄，省 STM32 flash。
- ⚠️ **熱替換要能真的即插即用（尤其會跑本地 PID 的控制末端）**：中繼器發現某位址是「新/空白模組」時，**從型錄把該位置的設定（校正、PID 增益、通道對應、設定點）推下去**（走進階/CFG 模式）→ 空白模組插上就自動變成該位置該有的東西。這是「直接替換」對**控制型**末端也成立的關鍵機制。
- 型錄裡每一筆仍各自符合 `device.schema.json`（module E 的驗證對象）。

## L. 控制細項 + 選料 + 測試（2026-08-20）

### ⚠️ 待對齊：`\n` 的語意（user 述 vs lib 定版不一致）
- **user 原意（重申）**：`\n`＝**該筆資料尚未傳完**（同一筆的分段，續等）；`\r`＝該筆傳完。
- **lib 目前定版**：`\n`＝**該筆已完、但後面還有下一筆**（批次分隔）；`\r`＝批次結束。
- 兩者對「單筆」完全一樣（都 `…\r`），**只有「一次回多筆」時 `\n` 意義相反** → 不阻 Stage 0–2（每次回一筆），但**批次功能實作前必須拍板**。傾向**照 user 原意**（比較簡單、合原始需求），屆時調整 lib 的 FrameDecoder + docs/02 §2。

### 控制協定/schema（暫訂通過，待框架對齊後寫定版）
- **SET 多鍵＝原子套用**：先全部驗證（範圍/合法）→ 全過才全套用；任一不合法則**全部不套用** + ACK 回報壞在哪個鍵。避免半套用的不一致狀態。
- **SET 需 ACK**（沒 CRC 時靠 ACK 確保寫到）。
- **PC 必須能 SET**（末端也要把狀態回報上 PC → 接客戶系統）。
- **緊急停止＝位址 0 廣播** `{"estop":1}` → 全體 `safe_state`。
- schema 加 `role:"controller"` + `control` 區塊（setpoint/kp/ki/kd/mode/pv_key/out）；每筆量測加 `channel`+各自校正。

### MCU「C 系列」澄清
- **沒有「C 系列特別適配 MicroPython」**。料號中的 `C`＝**48 腳封裝**（如 F103C8、F411CE），不是家族。
- 真的 **STM32C0** 家族＝超低階 M0+（RAM 6–36K）**跑不動 MicroPython**。MicroPython 甜蜜點是 **F4（F411 便宜）/F7/H7**（RAM≥64K）。

### 無線（暫緩）
- 手上無 WiFi 模組；**可能改 LoRa 或其他無線**。若走 LoRa → **STM32WL**（ST，MCU+LoRa 一顆，非陸）或 Semtech SX1262；LoRa **低頻寬（~0.3–50kbps）只適遠端稀疏節點，非骨幹**。骨幹仍首選有線 Ethernet(W5500)。

### 收發器庫存 / 測試

## M. 設備健康狀態機 + 熱插拔偵測（新增 2026-09-03）

> 你的問題：怎麼分辨一台設備「正常運作 / 壞掉 / 已拔除 / 剛更換」？

### 殘酷事實：bus 上「沒回應」分不出三種
**壞掉、拔除、斷電——在 RS485 上全都是「沉默」**，光靠有沒有回應無法區分。要分辨，得①**讓末端多報幾個欄位**、②**中繼器記住每個位址的歷史**、③（可選）**硬體加一支在位偵測腳**。

### 末端要多報的欄位（大多是 STM32 內建、零外加硬體）
末端回覆的 JSON 加三個欄位：

| 欄位 | 來源 | 用途 |
|---|---|---|
| **`ok`** | 韌體自我健檢（感測值在範圍內/自我測試過） | 分辨「活著但感測器壞」vs「整台沉默」 |
| **`up`** | `millis()`（uptime 毫秒/秒） | **`up` 歸零＝這台重開過或被換掉**；`up` 連續＝剛才只是抖動，同一台沒死 |
| **`rst`** | STM32 `RCC_CSR` 重置原因暫存器 | 開機後回報「上次為何重置」：上電(POR)/欠壓(BOR)/看門狗(IWDG)/軟體/腳位 → **把「斷電」「當機自救」「正常重開」分開** |

> `rst` 讓「沉默後回來」進一步細分：`up≈0 + rst=BOR/POR`＝**斷過電**；`up≈0 + rst=IWDG`＝**當機被看門狗救回**；`up≈0 + rst=PIN`＝被按 reset/剛插電。這些全是內建暫存器，免外加硬體。

### ID＝7 位指撥＝位址（你的決定，2026-09-03）
- **ID 就是位址（位置）**，由 7 位指撥設定（6 位址 + 1 功能位）。**位址已經在框架前綴裡了，所以 JSON 不需要另外再放一個 `id` 欄位**（重複）。
- ⚠️ **推論**：同一位置換一顆新板時 DIP 設成一樣 → **ID 一樣** → **`id` 無法分辨「同一顆回來」vs「換了實體新板」**。這在工廠可替換模組系統其實**沒關係**：位址＝邏輯身分，重點是「這個位置的模組活著且設定正確」，不是哪一片實體 PCB。
- **要真的分辨實體換板**（選配）：STM32 內建 **96-bit 唯一晶片 ID（UID）**，可當 `uid` 上報——免指撥、免外加。`uid` 變了＝真的換了實體板。你選用指撥當 ID，這個當**選配**，需要時再開。

### 狀態機（中繼器對每個位址維護）
中繼器對每個孩子位址記：`age`（上次成功回覆到現在）+ 上次的 `up`/`ok`，推出狀態：

| 狀態 | 判斷條件 | 中繼器動作 |
|---|---|---|
| ✅ **HEALTHY 正常** | 有回、`age` 小、`ok=1` | 正常快取 |
| ⚠️ **DEGRADED 活著但故障** | 有回、但 `ok=0` | 上報「感測器故障」，值標不可信 |
| 🟡 **STALE 可疑** | `age` > 1~2 輪詢週期 | 保留舊值+標 age，續觀察 |
| ❌ **GONE 消失** | `age` > 門檻（如 5s） | 上報離線；**壞掉/拔除/斷電分不出，統稱 GONE** |
| 🔄 **NEW 剛插入/更換** | 從 GONE/空 回來、且 `up≈0`（或 `uid` 變） | **從型錄把設定(校正/PID/通道/設定點)推下去**（CFG），即插即用 |
| 🔁 **RECOVERED 抖動恢復** | 從 STALE 回來、且 `up` 連續 | 同一台、沒真死，**不重推設定** |

門檻（stale/gone 幾秒）做成可調參數，Stage 實測校準（呼應 §E2、§K）。

### 要加的硬體（很少）
1. **7 位指撥開關**（已規劃）：6 位址 + 1 功能位。接法＝7 支 GPIO 各配上拉/下拉電阻；STM32 GPIO 充足直接接最簡單（省腳可用 74HC165 移位暫存器串讀）。
2. **在位偵測腳（選配，只有要硬分辨「拔除 vs 座著壞死」才加）**：
   - **背板式**：每插槽一支**最短的偵測腳**（插到底才接 GND），中繼器用 GPIO(上拉) 讀——腳通沒回應＝**座著壞死**（換板）；腳斷＝**被拔走**。槽多用 I/O 擴充(MCP23017)。
   - 剛好搭 §「插拔鐵律」：連接器 **GND 腳最長（先通後斷）＋偵測腳最短** → 插拔順序自動正確、又有在位訊號。
   - 純菊鏈 bus 不易中央偵測 → 不加，靠 `up`+`age` 就好。
3. **其餘零外加**：`up`(millis)、`rst`(RCC_CSR)、獨立看門狗 IWDG（卡死自動重開→變 NEW 可偵測）、UID（選配真序號）——全是 STM32 內建。

### 定版影響
- **schema（模組 E）**：`measurements` 同層加設備狀態欄位 `ok`/`up`/`rst`（`uid` 選配）。
- **末端韌體（模組 A）**：開機讀 `RCC_CSR` 存 `rst`、開 IWDG、每次回覆帶 `up`/`ok`。
- **中繼器（模組 B）**：cache slot 加狀態機（本次 C++ 版已有 fresh/stale/valid，擴成上表六態）。
- **PC（模組 D）**：依狀態上色（正常綠/可疑黃/離線紅/剛換閃藍），NEW→自動觸發型錄推設定。
- 這是「PC 端條件自動控制」的健康監測底層，**建議跟 §L 控制協定一起定版**。
